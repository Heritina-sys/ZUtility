# Contributing to ZUtility

ZUtility is the device collector of the ZK attendance platform. It is the only
component that touches hardware, and the only one that must run on Windows.

Read [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) and
[`docs/DEVICE-SDK.md`](docs/DEVICE-SDK.md) before changing anything — the punch
pairing logic is subtler than it looks, and the COM constraints are not
negotiable.

---

## You need Windows

This is not a preference. `zkemkeeper` is a registered 32-bit Windows COM
library; the `COMReference` in `ZKUtility.csproj` cannot resolve on Linux or
macOS, and `dotnet build` will fail there.

You also need the SDK **registered on the machine**, not merely downloaded.
Setup and verification: [`docs/DEVICE-SDK.md`](docs/DEVICE-SDK.md).

```powershell
git clone https://github.com/Heritina-sys/ZUtility.git
cd ZUtility
dotnet restore
dotnet build
dotnet run --project ZKUtility
```

### Without physical terminals

Most work does not need hardware. `Connect_Net` returns `false` for unreachable
devices and `AttendanceWorker` skips them with a warning, so the service runs
cleanly against an empty network — you simply get no punches.

To exercise the pairing logic, call `AttendanceService.ProcessLogs` directly with
a hand-built `List<DeviceLog>`. That method is pure with respect to the SDK: it
takes logs and a device IP, and returns event strings. It is the natural seam for
testing, and the obvious place to start if you want to add the test project this
repository lacks.

## Never commit

| | Why |
|---|---|
| `Interop.zkemkeeper.dll` | Generated by `tlbimp` at build time, machine-specific. |
| `bin/`, `obj/`, `.vs/` | Build output and editor state. 61 such files were tracked until September 2026 — about 70% of the repository's weight. |
| `*.csproj.user` | Personal launch settings. |
| Real device IPs of a customer deployment | Treat network topology as sensitive. |

`.gitignore` covers all of these. Before committing:

```powershell
git diff --cached --name-only
```

## Branching and commits

`master` is the default branch. Branch from it, one topic per branch.

| Prefix | For |
|---|---|
| `feat/` | New capability |
| `fix/` | Bug fix |
| `docs/` | Documentation only |
| `refactor/` | No behaviour change |
| `chore/` | Tooling, dependencies, CI |

[Conventional Commits](https://www.conventionalcommits.org/):

```
fix(worker): poll every 10s instead of every 1ms
feat(config): read device addresses from appsettings
refactor(service): remove superseded window-based pairing
```

Imperative mood, no trailing period, subject under 72 characters.

## Rules specific to this codebase

### Touching the pairing logic

`AttendanceService.ProcessLogs` decides whether a punch opens or closes a
session. Get it wrong and attendance records are silently incorrect — no
exception, no log, just wrong hours in a dashboard someone may use for payroll.

Before changing it, be able to answer:

- What happens to an employee who punches once and never again that day?
- What happens on a punch 299 seconds after the previous one? At 301?
- What happens to a punch whose timestamp is *earlier* than the last recorded
  one, e.g. after a device clock correction?
- What happens on service restart mid-shift?

The current answers are in
[`docs/ARCHITECTURE.md § 3②`](docs/ARCHITECTURE.md#-pairing-punches-into-sessions--zutility)
and its state-ownership table. If your change alters any of them, say so
explicitly in the PR.

### Touching the COM wrapper

`DeviceService` is the only file that references `zkemkeeper`. Keep it that way —
COM types must not leak into services, controllers or models, or the
Windows-only constraint spreads through the codebase.

`Disconnect()` must stay in a `finally` block. A leaked connection holds one of
the terminal's limited concurrent-session slots until it times out.

### Deleting commented-out code

There are large commented blocks in `Program.cs`, `AttendanceService.cs` and
`AttendanceWorker.cs`, including a superseded window-based pairing
implementation. **Deleting them is welcome.** Git remembers; a file at twice its
useful length does not help anyone.

Do it as its own `refactor:` commit, not folded into a functional change.

## Especially welcome

Roughly in order of value, from
[README § Known limitations](README.md#known-limitations):

1. **Fix the poll interval.** `Task.Delay(1, stoppingToken)` — one millisecond.
   Eight COM devices are hammered continuously. A one-character fix with a large
   effect.
2. **Move configuration out of source.** Device IPs, port, push URL and the
   300-second dedup window are all compiled in. A `Devices` section in
   `appsettings.json` bound to an options class would make this deployable
   anywhere.
3. **Persist the sync cursor.** `_lastSyncPerDevice` is a static field; a restart
   re-reads every device buffer and duplicates history in ZKAPI.
4. **Retry pushes with backoff.** Fire-and-forget loses records whenever ZKAPI
   restarts.
5. **Fix `POST /api/Device/sync`** — the `HttpClient` field is never assigned, so
   the endpoint always throws.
6. **Add a test project** around `ProcessLogs`. It needs no hardware.
7. **Delete the `WeatherForecast` scaffolding.**
8. **Sort out the DI lifetimes** — `AttendanceService` is registered three times.

Open an issue before starting on 2 or 3; both touch the contract with ZKAPI and
are worth agreeing on first.

## Before pushing

```powershell
dotnet format --verify-no-changes
dotnet build
```

CI builds on `windows-latest`. It cannot verify COM interop — no SDK is
registered on GitHub's runners — so a green build does not prove device code
works. Say in your PR whether you tested against real terminals.

## Reporting

- **Bugs and features** — [open an issue](https://github.com/Heritina-sys/ZUtility/issues/new/choose).
